# 31 — A hundred and fifty thousand rows in a real engine

Merged in #49.

The claim the whole design rests on had every part tested except the part a user
would notice. `tests/perf.rs` proves the *queries* stay cheap at 10k rows;
`SongTable.test.tsx` proves the virtualizer is *wired up* in jsdom — which has no
layout and therefore no scrolling, so every row is 0px tall and the number
rendered is whatever the mock decided.

- Rows are **inserted, not scanned**: 150k real files would be gigabytes and
  minutes to produce a worse test, and what is under test is the table, not ingest.
  The seeding command refuses in any build a user could install — `e2e_only` is a
  bare `Err` there, since the code that could say yes is behind the `wdio` feature
  — and a unit test asserts that in the configuration a user gets.
- **Strict where it is exact:** the count reaches the far end, the scroll extent
  passes a million pixels, the last row is real rather than a placeholder, and the
  DOM holds under two hundred rows — before a scroll, after scrolling to the
  bottom, after a re-sort, and after a jump into the middle.
- **A ratio where it is performance:** a cold far page against a cold near page.
  That is the design's actual promise — cost does not grow with library size — and
  a ratio measures the app rather than the runner. The cache is emptied through
  the UI's own route (a re-sort), because measuring against a warm cache measures
  the cache.
- The first version asserted ten- and fifteen-second ceilings and printed nothing,
  which is worth very little. **Every timing is printed now**; the log is where a
  trend lives.
- What the first runs measured (debug build, 150,006 rows): near page 454–482ms,
  far page 528–1095ms, full re-sort to first painted row 262–300ms. So deep paging
  *is* more expensive — `OFFSET` walks the index — by a small constant factor, and
  the run-to-run spread is as wide as the effect. **Read one run as one sample:**
  the first pass showed no difference at all and the second contradicted it.

The driver delivers no `dblclick` through the Actions API; dispatch the event React
listens for instead.
